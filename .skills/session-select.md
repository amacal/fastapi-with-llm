## Steps

1. **Sibling repo awareness (informational only — skip entirely if `GITHUB_TOKEN` isn't set, or if this repo's own `origin` remote can't be resolved).** No local clone is kept between sessions — this reads each sibling's live default branch fresh, every time, directly from GitHub; nothing here is ever pulled, updated, or left on disk afterward.
   - Resolve the owner from this repo's own remote, never hardcoded: `git remote get-url origin`, parsed for the `<owner>` segment (works for both `git@github.com:<owner>/<repo>.git` and `https://github.com/<owner>/<repo>.git` forms).
   - List candidates: `curl -s -H "Authorization: token $GITHUB_TOKEN" "https://api.github.com/users/<owner>/repos?per_page=100"`, filter to names ending in `-with-llm`, excluding this repo's own name.
   - Qualify each candidate: `curl -s -o /dev/null -w '%{http_code}' -H "Authorization: token $GITHUB_TOKEN" "https://api.github.com/repos/<owner>/<candidate>/contents/.skills/session-select.md"` — `200` means it uses the full select/plan/close/verify/retro architecture and counts as a real sibling; anything else (e.g. a repo deliberately built without it) is skipped, never assumed.
   - For each qualifying sibling, read its actual default branch from `https://api.github.com/repos/<owner>/<candidate>` (the `default_branch` field) — never assume `master` or `main`.
   - Shallow-clone exactly that branch into a throwaway directory, read what's needed, delete it before this step ends: `git clone --depth 1 --branch "<default_branch>" "https://x-access-token:$GITHUB_TOKEN@github.com/<owner>/<candidate>.git" .tmp/sibling-<candidate>`, then `ls .tmp/sibling-<candidate>/.history/*/*.yml | sort | tail -6` and a quick `Read` of just the `date`/`title` fields (or its `summary.txt` equivalent under `.index/sessions/`), then `rm -rf .tmp/sibling-<candidate>`.
   - Purpose is situational awareness only: how recently and how intensely the user has been working elsewhere, and on what topics — never used to justify or rule out a FastAPI candidate's prerequisites (this repo's scope stays self-contained regardless of what's happening in a sibling repo), and never used to infer personal/psychological conclusions. A sibling repo showing recent activity on a pattern this repo could reasonably reuse (e.g. a configuration-management repo's own idempotent-check discipline, relevant to how an exercise here verifies a dependency's effect) is still worth naming here as color — but a genuine concept-overlap (not just topical activity) is handled separately, in step 1c, which *does* deliberately feed into candidate selection; keep the two apart in your report.
   - Report this as its own clearly labeled section in step 7, separate from the candidate list, so the calling conversation can mention it in passing if relevant instead of blending it into candidate rationale.

1b. **Retention checks due — check and report first, before anything else.** `ls .index/cold-runs/*.yml 2>/dev/null`, `Read` each. Any with `due_date` today or earlier and `status: pending` goes at the very top of your report, ahead of the candidate list in step 7 — not as one option among several, as the thing to do first. A due retention check is never optional breadth; only its exact timing is the calling conversation's call, never whether to do it at all.

1c. **Cross-repo overlap check**, same gate as step 1 (`GITHUB_TOKEN` + resolvable owner) and reusing the same ephemeral clone already made there — don't clone twice. While a qualifying sibling's clone is present, also `Read` its `.index/sessions/*/concepts.yml`/`capabilities.yml`/`meta.yml` for any concept that genuinely overlaps a candidate you're about to propose here, and note its recorded `status` (`demonstrated`/`retained`) there — read live, never assumed or recalled from a prior run. See CLAUDE.md's "Cross-repo transfer" for the three honest outcomes (cite, bridge, or independent) this feeds into — this step only *surfaces* the overlap; deciding which outcome fits is the plan agent's job (`.skills/session-plan.md`), not this one's. Never resolve overlap from a bare matching word in `concepts.yml` — name the specific sibling session and its status, or don't claim overlap at all.

2. **Done set.** `ls .index/sessions/` (each directory's `meta.yml` `title:` field is the exact Concept Title, and its `target:` field the target environment) — this IS the done set. Cross-check against the exercise directories actually present under `in-process/` and `live-server/`. Fall back to reading every `.history/*/*.yml` in full only if `.index/` looks stale/incomplete (e.g. an exercise directory with no matching `.index/sessions/*/meta.yml` entry).

3. **Dependency graph.** `grep -rl "<concept title>" .index/sessions/*/prerequisites.yml` for reverse "required-by" lookups; `Read .index/sessions/<slug>/derived_from.yml`/`unlocks.yml` for a session's own forward relationships — genuine prerequisites already kept separate from softer `uses_concepts.yml`/`related_to.yml`. `ls .index/branches/` + `Read` each for branch structure, `ls .index/open-gaps/*/` + `Read` each for "what's underexplored". `.history/` carries no dependency field by design — if `.index/` looks stale, re-derive from notes/exercise files directly, never from a `.history/` `Depends on`/`Unlocks` field (none exists). Use `grep -l '"<title>"' .history/*/*.yml` or `grep -r "<term>" .history/*/*.yml` only for session-event citations (a specific bug, a specific wrong prediction) when needed.

4. **Target position.** Run `.index/schema.yml`'s `target_frequency` query (`grep -h '^target:' .index/sessions/*/meta.yml | sort | uniq -c | sort -rn`) to see, concretely, how sessions are distributed across `in-process` and `live-server` — cite the actual counts when a candidate would rebalance coverage. For any pattern already done `in-process`, check whether the same pattern is a viable, interesting `live-server` candidate too (see CLAUDE.md's "Cross-target comparison") — `grep -rl "<concept>" .index/sessions/*/related_to.yml` shows if that comparison has already been made. Propose a `live-server` candidate specifically whenever a topic genuinely needs something only a real running process can honestly teach — real concurrency under I/O, lifespan timing, background-task timing after the response is sent, or static-file HTTP semantics (see CLAUDE.md's "Target environments") — rather than defaulting to `in-process` out of habit.

5. **Generate exactly 3–5 candidates.** Per candidate:
   - Confirm not already in the done set.
   - Confirm its full prerequisite chain is already covered — except the stepping-stone exception in "Session selection", named explicitly with the larger target it unlocks.
   - Classify: harder variant/extension, same-idea-different-target (cross-target), gap-filling, or stepping-stone.
   - 1-2 sentences on why it's interesting given what's done.
   - Its prerequisite chain (existing sessions/exercises it draws on).

6. **Force genuine breadth.** Don't let all candidates be the next link in the most recent chain. Run `.index/schema.yml`'s `concept_frequency` query (`grep -h '^- ' .index/sessions/*/concepts.yml | sed 's/^- //' | sort | uniq -c | sort -rn`) to see which areas are saturated versus barely touched — cite the actual counts (e.g. "dependency-injection: 4 sessions, background-tasks: 0") when justifying a candidate. Explicitly consider the full trajectory named in CLAUDE.md's Scope (routing/parameters, Pydantic, dependency injection, async, middleware, error handling, static files, testing, the OpenAPI schema as a verification tool) and target-breadth angles, include at least one cross-target candidate if the done set supports it. This frequency count is a descriptive signal only — it does not replace the hand-curated judgment in `.index/selection-context/`, which stays a human/agent judgment call, not a formula.

7. **Report back**, in this order: (a) any retention check due from step 1b, first and unmissable; (b) a plain list of the candidates (title, target environment, classification, rationale, prerequisite chain), each flagged with any cross-repo overlap found in step 1c (sibling repo, title, status there); (c) the sibling-repo situational-awareness section from step 1 (which repos exist, whether each was refreshed or skipped and why, the handful of recent session facts). Not a user-facing menu, no questions asked — structured findings for the calling conversation to present interactively.
